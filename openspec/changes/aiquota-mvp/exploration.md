### Per-Provider Integration Findings

**Claude** (`repos-referencia/claude-quota-tracker/src/core/quotaService.ts`, `src/utils/chromiumService.ts`, `src/utils/types.ts`, `README.md`):
- Endpoint: `GET https://claude.ai/api/organizations/{orgId}/usage`, header `accept: */*`, `anthropic-client-platform: web_claude_ai`, `credentials: include` (cookie-based).
- Auth: cookie `sessionKey` (value `sk-ant-sid01-...`) + cookie `lastActiveOrg` = org UUID. Both cookies are injected via Playwright `context.addCookies(...)` scoped to domain `.claude.ai`.
- **Cloudflare workaround**: launches a real (headed, `--headless=new` flag) Chromium via `playwright-core`, navigates to `https://claude.ai/`, polls `document.body.innerText` for absence of "Verifying you are human" / "needs to review the security" strings (up to 30s timeout), waits an extra 3s to "settle", THEN calls `fetch()` from inside `page.evaluate()` so the request carries real browser fingerprint/cookies. It also spoofs `navigator.webdriver`, `navigator.permissions.query`, and injects a fake `window.chrome` object to reduce bot-detection signals.
- Response shape (`ClaudeUsageResponse`): `{ five_hour?: { utilization: number, resets_at: string }, seven_day?: {...}, seven_day_oauth_apps?, seven_day_opus?, seven_day_sonnet?, extra_usage? }`. `utilization` is already a 0–100 percentage; no separate `limit`/`usage` counts.
- **Org ID discovery gap**: the reference repo does NOT auto-derive the org ID. README instructs the user to manually copy it from DevTools Network tab or from `claude.ai/settings/account`. The PRD's MVP requirement ("login integrado ... obtener Org ID de la API") has no working precedent in this codebase — the design phase must find/verify an actual "list my organizations" endpoint, or fall back to parsing `lastActiveOrg` cookie value if claude.ai sets it after login. **This remains an open verification gap** (unlike the Codex gaps below, which are now resolved).
- 401/error handling: reference repo has no explicit 401-specific branch; throws generic `HTTP {status}: {statusText}` on non-200. No refresh-token flow exists for Claude (session cookies aren't refreshable — re-login is the only recovery path).
- Browser lifecycle: one long-lived `Browser`/`BrowserContext` reused across polls; a new `page` per fetch. Maps to "one Electron `session.fromPartition` per Claude instance" for our multi-instance model.

**Codex/OpenAI** (`repos-referencia/codex-quota-stats/extension.js`, `scripts/read_codex_usage.py`, `test/extension.test.js`, `README.md` — verified locally, VERIFIED AND CORRECTED against earlier WebFetch-only findings):
- **Endpoint — CONFIRMED**: `const REMOTE_USAGE_URL = "https://chatgpt.com/backend-api/wham/usage"` (`extension.js:10`), called via a plain Node `https.request` GET (`httpsGetJson`, `extension.js:297-327`). No Cloudflare workaround exists or is needed for this endpoint — no browser/Playwright dependency at all for Codex's remote call.
- **Auth flow — CONFIRMED**: `loadAuthData()` (`extension.js:192-227`) reads `{codexHome}/auth.json` where `codexHome` resolves via `getCodexHome()` (`extension.js:329-336`): user setting → `CODEX_HOME` env var → `path.join(os.homedir(), ".codex")`. Extracts `tokens.id_token`, `tokens.access_token`, `tokens.account_id`. JWT payloads are base64url-decoded WITHOUT signature verification (`parseJwtPayload`, `extension.js:229-245`) to read claims under `https://api.openai.com/auth` (`chatgpt_account_id`, `chatgpt_plan_type`) and `https://api.openai.com/profile` (`email`). Account ID resolution priority: user-configured setting > `auth.json`'s `tokens.account_id` > JWT claim `chatgpt_account_id`.
- **Request headers — CONFIRMED**: `Authorization: Bearer {accessToken}`, `Accept: application/json`, `originator: codex_vscode` (const `REMOTE_ORIGINATOR`), `User-Agent: local-codex-stats`, plus `ChatGPT-Account-Id: {accountId}` when known (`fetchRemoteUsage`, `extension.js:279-295`).
- **Refresh token — CONFIRMED ABSENT**: `auth.json`'s `tokens` object, as read by this extension, exposes only `id_token`, `access_token`, `account_id` — no `refresh_token` field is read or referenced anywhere in `extension.js`. **401/error handling — CONFIRMED MINIMAL**: `httpsGetJson` only checks the HTTP status range (200–299 vs not) and rejects with a generic `Usage API returned {status} {statusText}` message; there is no status-code branching (no special 401 case), no retry, and no refresh-token exchange anywhere in the codebase. `refreshStats()` (`extension.js:91-117`) uses `Promise.allSettled` to isolate the local-SQLite fetch from the remote-quota fetch, so a remote auth failure doesn't block local data (or vice versa) — this per-source isolation is a good pattern to carry into our adapter design. **Conclusion for design**: the PRD's assumption of an available `refresh_token`-based recovery path for Codex has NO precedent in this reference and must be designed/verified independently (e.g., against the actual Codex CLI's own OAuth refresh behavior, not this extension, which simply surfaces the failure and expects the user to have re-authenticated the Codex CLI externally).
- **Response shape — CONFIRMED via test fixtures** (`test/extension.test.js` `sampleRemoteUsageData()`, lines 136-150): 
  ```
  {
    rate_limit: {
      allowed: boolean,
      limit_reached?: boolean,
      primary_window: { used_percent: number, reset_after_seconds?: number, reset_at?: number (epoch seconds) },
      secondary_window: { used_percent: number, reset_after_seconds?: number, reset_at?: number }
    },
    additional_rate_limits?: [{ limit_name? | metered_feature?, rate_limit: { primary_window, secondary_window } }]
  }
  ```
  Field names are generic (`primary_window`/`secondary_window`), NOT `five_hour`/`seven_day` as the PRD/Claude-style naming might suggest — **but the UI labels `primary_window` as "Last 5 hours" and `secondary_window` as "Last 7 days"** (`buildTooltip`/`appendQuotaSummary`, `extension.js:408-423`), confirming the semantic mapping is 5-hour/7-day even though the wire field names differ from Claude's. **Reset semantics — CONFIRMED**: both `reset_at` (absolute epoch-seconds timestamp) and `reset_after_seconds` (relative duration) may be present; test fixtures populate only `reset_after_seconds`, and display logic (`formatReset`/`formatResetSummary`) prefers the relative form when available, falling back to the absolute timestamp. Treat both as optional/either-or in the adapter's normalization.
- **Windows path handling — CONFIRMED**: `getCodexHome()` uses `os.homedir()` which resolves to `%USERPROFILE%` on Windows, so the default path is exactly `%USERPROFILE%\.codex`, matching the PRD. No Windows-specific branching needed beyond what `os.homedir()`/`path.join` already provide.
- **New finding not in the original WebFetch summary — local SQLite/Python dependency**: this extension ALSO reads two local SQLite databases (`logs_2.sqlite`, `state_5.sqlite` under Codex home) via a bundled Python helper script (`scripts/read_codex_usage.py`), invoked through `execFile(pythonCommand, [scriptPath, "--codex-home", codexHome])` (`extension.js:247-277`), requiring a system Python interpreter. This path produces **local token-count data** (`current_thread`, `latest_response`, and `windows.five_hours`/`windows.seven_days` — note: THIS is where `five_hours`/`seven_days` naming actually appears, for local token totals, not the remote quota percentages) — a completely separate concern from the remote `wham/usage` quota-percentage endpoint. **Design implication**: AIQuota's MVP only needs the remote quota-percentage path (`auth.json` + `wham/usage`); the local SQLite/Python token-counting path is unnecessary extra complexity (external Python dependency, SQLite schema coupling to Codex's internal storage) that should NOT be replicated for the MVP's quota-tracking goal — it's solving a different problem (context/token telemetry) than "how much quota is left."
- Dual-auth cascade (`~/.codex/auth.json` first, integrated chatgpt.com web login as fallback) is a PRD requirement with **no precedent in this reference** (it only reads `auth.json`; there is no web-login fallback code at all) — must be designed fresh, same as previously assessed.

**OpenCode Go** (`opencode-go-monitor/opencode-go-monitor/src/fetchers/*.ts`, `src/domain/*.ts`, `src/storage/credentials.ts`) — Phase 2 scope per PRD, but the most architecturally reusable reference:
- Dual-strategy adapter: `ApiFetcher` (`GET https://console.opencode.ai/zen/go/v1/usage`, header `Cookie: auth={authCookie}`) with `FetcherSelector` currently hard-forcing the `ScrapingFetcher` strategy (API path is commented out/disabled with `TODO: Re-enable API fetcher when endpoint is stable`).
- `ScrapingFetcher` hits `GET https://opencode.ai/workspace/{workspaceId}/go` with spoofed headers, then regex-parses SolidJS SSR hydration payload: `rollingUsage:$R[\d+]={status:"...",resetInSec:\d+,usagePercent:\d+}` (and `weeklyUsage`/`monthlyUsage`). Throws `ParseError` if all three windows are unmatched.
- Normalized shape: `QuotaSnapshot { timestamp, rolling, weekly, monthly, source: 'api'|'scraping' }`, each window `{ status: 'ok'|'error'|'unknown', usagePercent, resetsInSeconds }`.
- `FetcherSelector` implements exponential backoff on failure (`BACKOFF_STAGES = [60,300,900,1800]` seconds) — reusable pattern for the MVP scheduler's per-instance failure handling.
- Credentials abstraction (`CredentialsStorage`) wraps a `SecretStorageLike` interface (`get/store/delete`) — directly analogous to what Electron's `safeStorage` + a small key-value store would need. `maskCookie()` for safe debug logging is a good convention to carry over.
- Domain errors are typed (`CredentialsError`, `ParseError`, `NetworkError` with `status`) — clean pattern for the `QuotaProvider` adapter interface's error surface.

### Mapping to PRD's QuotaProvider / ProviderInstance Model
The PRD interface: `QuotaProvider { id, configure(), fetchQuota(): QuotaWindow[], authStatus() }`, with N `ProviderInstance { instanceId, providerId, label, credentialsRef }` per provider.

- **Codex adapter** (MVP): no Electron session needed for the CLI-token path (plain HTTPS call with a bearer token read from local filesystem state) — confirmed simplest path, matching PRD's stated priority. `configure()` = cascade: try `~/.codex/auth.json` (or `%USERPROFILE%\.codex\auth.json`) → if absent/expired, open an isolated `session.fromPartition` window to chatgpt.com (net-new design, no reference precedent). `authStatus()` must distinguish "no CLI, no web session", "token present but request failed" (no 401-specific signal is available from the API itself per the reference — must treat any non-2xx as "needs reconnect" rather than assuming a refresh path), "healthy".
- **Claude adapter** (MVP): always needs its own `session.fromPartition('persist:claude-{instanceId}')`. `configure()` = open BrowserWindow to claude.ai, wait for login, read `sessionKey` cookie via `session.cookies.get()`, then call the (still-to-be-verified) org-list endpoint to get `orgId`.
- **fetchQuota()**: Codex needs only a plain HTTPS/fetch call once the token is known (no Cloudflare concern at all for `chatgpt.com/backend-api/wham/usage`). Claude needs the "real browser context" treatment — Electron's session already provides a real Chromium fetch context, so the reference repo's Playwright-launch + Cloudflare-wait dance may be reducible to "make sure the window has visited the site once so CF clears the challenge, then reuse cookies for background fetches." Needs a design-time spike (risk below).
- N-instance readiness: even though MVP exposes one account per provider, the adapter contract, credential keying (by `instanceId`), and session partition naming should be built for N from day one per PRD explicitly.

### Electron Architecture Considerations
- **Main process**: owns the polling scheduler (per-instance timer, 1–60 min configurable, default 5 — mirrors `opencode-go-monitor`'s 300s default and `claude-quota-tracker`'s `MIN_FETCH_INTERVAL` guard), tray icon/menu, native notifications (one-shot per threshold-crossing per window), and `safeStorage`-encrypted credential persistence keyed by `instanceId`.
- **Isolated login sessions**: `session.fromPartition('persist:{providerId}-{instanceId}')` per PRD §5.3 — critical for multi-account isolation. Only Claude's login flow and Codex's web-login fallback need this; Codex's primary `auth.json` path needs no BrowserWindow at all.
- **Popup renderer**: React + Vite, `contextIsolation: true`, `nodeIntegration: false`, typed preload script exposing a narrow IPC surface via `contextBridge.exposeInMainWorld`. IPC channel names/payload types should be defined once in a shared module imported by main and preload/renderer.
- **Tray**: color aggregation (green/amber/red/gray) as a pure derived function `computeTrayState(snapshots): TrayState`, independently testable.
- **Notifications**: native `Notification` API with a small "already notified for this window generation" set keyed by `(instanceId, windowType, resetsAt)` so a threshold crossing notifies once and resets only when `resetsAt` changes (no reference repo demonstrates this — new design work).
- **electron-builder**: AppImage + .deb (Linux), NSIS .exe (Windows) — no macOS target for MVP; auto-update deferred to Phase 2.

`openspec/config.yaml` already mandates that the first change introducing a test runner sets up TDD tooling before/alongside the first testable feature — Vitest is the clear choice (used by `opencode-go-monitor` and testable via Node's built-in `test` runner pattern in `codex-quota-stats`; works for both Node/main-process logic and Vite-based renderer).

### Approaches (Cloudflare/session strategy — now scoped correctly to Claude + Codex's *web-login fallback only*, since Codex's primary `auth.json` path needs no browser at all)
1. **Electron BrowserWindow session reuse, background `net.fetch`** — Pros: no extra Chromium bundle. Cons: unverified whether Cloudflare's cleared-challenge state survives once the window is hidden/closed and fetch runs from main-process context. Effort: Medium.
2. **Embed Playwright-core inside Electron** (port reference repo as-is) — Pros: proven to work today for Claude. Cons: bundles a second Chromium alongside Electron's own, conflicts with the PRD's <150MB RAM target and installer size. Effort: Medium-High.
3. **Hidden BrowserWindow + `webContents.executeJavaScript` fetch** — Pros: closest match to the proven pattern (real JS/browser context) without a second Chromium binary. Cons: needs one hidden window kept alive per active login-dependent instance; needs re-challenge detection. Effort: Medium.

### Recommendation
Approach 3 (hidden BrowserWindow + `executeJavaScript` fetch) for Claude's fetch path and for Codex's web-login fallback only — this scope is now smaller than originally assessed, since Codex's primary path (CLI token from `auth.json`) is a plain authenticated HTTPS call with zero Cloudflare/browser concern, confirmed against the real source. Validate Approach 3 with an early throwaway spike before locking the design. Build and validate the Codex CLI-token path first, exactly as the PRD prioritizes, and explicitly do NOT replicate the reference extension's local-SQLite/Python token-reading path — it solves a different problem (context/token telemetry) than quota tracking and would add an unnecessary Python runtime dependency to the MVP.

### Risks
- **Claude org-ID auto-discovery has no reference implementation** (still open). The PRD requires deriving org ID automatically after login; the reference extension requires manual DevTools copy-paste. An actual "list organizations" endpoint must be found/confirmed during design, or the MVP must fall back to reading a cookie/redirect that reveals the active org (e.g. `lastActiveOrg` cookie set by claude.ai itself after login, unconfirmed).
- **Cloudflare-clearing strategy for background (non-visible) polling is unverified** for Claude. All reference evidence is Playwright-based with a live page navigation; Electron's approach (hidden window vs `net.fetch`) needs a spike before committing to a design. (No longer a concern for Codex — its remote endpoint has no Cloudflare gate per the verified source.)
- **Codex 401/refresh-token recovery has no working reference** (confirmed, not just suspected) — `codex-quota-stats` treats any non-2xx as an undifferentiated error and relies on the user having a valid `auth.json` (i.e., a healthy Codex CLI session) already; it never attempts a refresh. AIQuota's own recovery UX (PRD: "detección de 401 + notificación de reconexión") must be designed independently — likely "prompt to re-run/re-login the Codex CLI, or fall back to the web-login flow" rather than any in-app token refresh, since no refresh mechanism is observable from a VS Code/Electron client.
- **Notification "no spam" semantics** need a precise state machine (per instanceId + windowType + resetsAt) — not present in any reference repo.
- **RAM budget (<150MB at rest)** is a real constraint against Approach 2 (embedding Playwright) and even partially against Approach 1/3 if multiple hidden BrowserWindows must stay resident per instance — needs measurement once a prototype exists. Confirmed Codex does NOT need this budget concern at all for its primary path.
- Both Claude and Codex reference implementations are unofficial reverse-engineered API clients (no public docs) — PRD's own risk table already acknowledges breakage risk; adapters must be versioned and isolated per PRD §6.
